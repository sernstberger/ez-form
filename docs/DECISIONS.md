## #9 + #66 — label placement axis

- Placement is its own axis (`labelPlacement: 'floating' | 'stacked' | 'start'`), not a fourth MUI `variant`: `TextFieldVariants` is a closed union with no `*PropsVariantOverrides` to augment and the runtime picks the input component from a fixed map, so a fourth value neither typechecks nor renders — cost if wrong: revisit if MUI ever adds the augmentation interface.
- `floating` stays the **library** default; `createEzFormTheme()` sets `EzForm.defaultProps.labelPlacement = 'stacked'`. DESIGN.md's frame is "components ship unstyled; this file is the taste", so #9's "make it the default" is satisfied where ez-form has a default look, and a consumer on plain `createTheme()` gets no taste they did not ask for (PHILOSOPHY rule 2) — cost if wrong: one theme line for a consumer who expected stacked out of the box; imposing taste from `src/` is the mistake the philosophy names.
- The placements are CSS on the one `FormControl` box every field's root already is (label, control, helper text, in that order), not a re-composition of each family's label — so no markup moves and `<label for>` / `aria-labelledby` / `aria-describedby` / the required marker are byte-identical under all three — cost if wrong: a field whose root is not a `FormControl` needs its own rule; all of them are (`FileField` and `OtpField` included, `AddressField` composes ez-form fields).
- The rules live once on `<Form>`'s existing `EzForm` Root slot rather than a new `Ez*` key per family, so `theme.components.EzForm.styleOverrides.root` reaches every one and `TextField` / `Select` / `Autocomplete` stay the pure pass-throughs PHILOSOPHY's checklist calls for — cost if wrong: a field rendered outside a `<Form>` is unstyled, which is already a guarded error.
- `stacked` closes the outline notch in CSS rather than threading `slotProps.input.notched` through every field — cost if wrong: a consumer's own `notched` under `stacked` loses, the same precedence the preset's `MuiOutlinedInput.defaultProps` already has.
- `start` is a two-column grid, not `flex-direction: row`: the box has three children and a row would put the helper text in a third column — cost if wrong: none found; the grid also survives a field rendering extra children.
- `Checkbox`/`Switch` (`FieldFrame`'s `labelAs="control"`) opt out of `start`'s grid — their label is inside the single `<label>` that is the click target — cost if wrong: a mixed-looking settings row; the alternative shrinks a 24×24 target, a WCAG failure.
- The axis is read in `useEzField`, the one hook every field already calls, rather than a new wrapper component — cost if wrong: a future field that binds without the hook misses it, and the contract line catches that.
- The preset keeps **both** the theme-wide `MuiInputLabel`/`MuiOutlinedInput` stacking and the new `EzForm` default: the former reaches a consumer's own bare `<MuiTextField>` outside any `<Form>`, which the form-scoped axis cannot — cost if wrong: one redundant rule, agreeing with the other.

## #130 — `start`'s breakpoint fallback

- Every `start`-only declaration is scoped under `theme.breakpoints.up(labelPlacementBreakpoint)`, so below the breakpoint a `start` box simply **is** `stackedBox` — replacing a fallback that applied the grid unconditionally and undid it under `down(…)` — because a hand-written reset list is a list you can forget from, and `alignItems` was forgotten: harmless row alignment in a grid, but the fallback re-declared the box as a flex column where `align-items` is the *cross* axis, so every control shrank to its intrinsic width on a phone (measured in Chrome at 380px: a Select 46px and a TextField 194px against `stacked`'s 349px, while the box itself was 349px in both) — cost if wrong: a theme overriding placement CSS must now out-specify a `@media (min-width…)` block to beat a `start` rule; `EzForm.styleOverrides.root` still reaches everything and its test still pins that.
- The regression test asserts the **CSS shape** — that `align-items`, `display:grid`, `grid-template-columns`, `grid-column`, `grid-row` and `padding-top` appear on a `start` selector only inside a min-width block, and that the fallback box equals the `stacked` box declaration for declaration — rather than a computed width, because jsdom has no layout and evaluates no media queries, and a browser is not in the test gate — cost if wrong: a future defect that is not a leaked declaration is missed; the browser measurements are recorded on #130.
- Tests that previously read the grid off `getComputedStyle` now read the emitted rule: under this shape the grid lives inside a media query, which jsdom never applies, so the old assertions would have silently reported the fallback — cost if wrong: the assertions are one step further from what a user sees, which the browser check on the issue compensates for.

## #131 — placement polish

- A `legend` label under `start` is **floated** (`float: inline-start`, plus the column width), not given a `padding-top`: the 40px offset was not padding but the CSS *rendered legend* rule — a `<fieldset>`'s `<legend>` is pulled out of the fieldset's formatting context and painted above the content box, so `grid-column: 1` computed on it and did nothing, leaving it full-bleed at its intrinsic width with the control box starting below it (measured in Chrome: legend 94px wide, group 31px lower; the first option's own 9px `SwitchBase` padding made up the rest). A floated legend is by definition no longer a rendered legend, so it rejoins the grid — verified level (`deltaTop: 0`) for RadioGroup, CheckboxGroup, Rating, Slider and ToggleButtonGroup — cost if wrong: a browser without logical-float support left-floats under RTL; the width has to be restated because a float sizes to content.
- No new themeable padding for the legend: with the float alone the residual to centre-match the first option's text is 1.5px, smaller than the offset the plain text fields already ship with, so a knob to correct it would be a literal with no reason to exist — cost if wrong: a theme can already reach the legend through `EzForm.styleOverrides.root`, and a knob can be added later without a break.
- The floating **story** sections render under a local stock `createTheme()` provider rather than a new `parameters.theme` opt-out in the preview: the preview picks the theme from the `theme` toolbar global that every story obeys, and a competing story-level parameter would mean the toolbar silently does not apply to some stories. Wrapping a section is ordinary story styling (PHILOSOPHY rule 2: `src/` may not style, stories may) — cost if wrong: switching the toolbar to "Stock MUI" makes those sections match their neighbours, which is honest, because there they are the same.
- The description gap is keyed on the **form containing** a non-floating field (`&:has(.EzFieldLayout-stacked) .EzForm-description`), not on the description being that field's sibling: `<Form>` renders its description above three context providers and a consumer's children normally sit in their own `<Stack>`, so a `+`/`~` selector between the two almost never matches. `floating` is deliberately excluded — its first element below the description is the input box, whose label is inside the outline, and MUI's own spacing already gives the same 16px — cost if wrong: jsdom does not implement `:has()`, so this one rule is pinned by its emitted text and measured in Chrome (0px before, 16px after) rather than by a computed margin.
- `formClasses` moves from `Form.tsx` to `src/Form/formClasses.ts` so the placement CSS can name `EzForm-description` without closing an import cycle (`Form.tsx` already imports `labelPlacementStyles`); it is re-exported from `./Form`, so the public path is unchanged — cost if wrong: one more file.

This was already failing on `main` before this branch. ## #28 — public `BoundField`

- One component, not two: `FieldFrame` is renamed to `BoundField` and exported, and the seven fields that rendered through it move to the public prop names (`renderControl` → `render`) — a thin public wrapper would duplicate the whole prop list and add a second binding path to keep in step, so each of the four fixes a consumer cannot make unaided (the `field.ref` fork that registers the focus target #98, the `aria-describedby` merge #102/#104, the empty-`aria-labelledby` guard #100, the `aria-label` routing #99) would have two homes; the rename touches 7 files mechanically and 0 behaviours — cost if wrong: the public prop surface is now also the internal one, so an internal-only prop cannot be added without it becoming API.
- `componentName` stays and is public, defaulted to `'BoundField'` — it is what the "must be rendered inside `<Form>`" throw and both dev warnings name, so a consumer wrapping their own control wants their own name in those messages; hiding it would make every consumer's warning say `BoundField`, which names nothing — cost if wrong: one more public prop, a string with a working default.
- `labelAs` gains `'none'` as the third mode and the public default: the frame renders no label element and hands back `displayLabel`/`labelId`/`controlId`/`labelRequired` — neither existing mode fits a control the frame knows nothing about (`control` wraps it in MUI's `FormControlLabel`, `legend` renders a `<fieldset>`), and the mode that renders no markup is the only one that cannot be wrong about it; the seven internal fields state their mode explicitly and are unaffected — cost if wrong: a consumer who wanted `FormControlLabel` writes `labelAs="control"`; the failure is a missing label they can see, not a silent a11y hole.
- `bound` grows `nameA11y`, `displayLabel`, `labelRequired`, `helperText`, `helperTextId` and `controlId`, all additive and all ignored by the frame family — the seven fields route `aria-label` to the control through `{...rest}`, which a render prop does not have, so without `nameA11y` the public path reproduces #99 exactly (name on the `FormControl` wrapper, axe clean, control anonymous); `controlId` is generated by the frame so `labelId`/`controlId` are a matched pair — cost if wrong: six unused keys on an object destructured by name, zero runtime cost since every one was already computed.
- The dev-mode no-accessible-name warning stays props-based, not DOM-based — `warnMissingLabel` deliberately checks the props before anything is painted and its own doc records the trade; a DOM check needs a post-commit effect plus an accname implementation and would still only be a warning. The public path is already covered by the same call. What was added instead is the contract test that proves the *rendered* control is named (`getByRole(role, { name })`, the assertion shape #99/#100 were caught by) — cost if wrong: a consumer naming their control from inside `render` gets a false warning; that false positive already exists for all 24 fields and has never been reported.
- The reference control is a plain `<input type="text">` in `src/test/ReferenceControl.tsx` with no MUI inside `render`, and it runs the FULL `describeFieldContract` with **nothing exempt** — a bare input is the case a consumer actually has and the only one where a failure is unambiguously ours rather than a widget's; wrapping a MUI control would let MUI's own label/helper machinery cover for a `bound` member `render` forgot — cost if wrong: a line that genuinely cannot pass needs an exemption with a reason, earned by a red test rather than assumed.
- `BoundField` registers `EzBoundField` `defaultProps` only — no `styled` slot and no `boundFieldClasses`, because it renders MUI's `FormControl`/`FormHelperText` unchanged and a class hook onto markup the consumer's `render` does not control would be a promise about markup that is deliberately not API — cost if wrong: a theme wanting the wrapper reaches `MuiFormControl`, already true for the seven internal fields.
- Generic over `TValue` with no default at the component, inferred from `rules` or stated explicitly; a bare `<BoundField name render>` infers `unknown` — the honest answer, and it forces the consumer to say what the field holds — cost if wrong: one explicit type argument at a call site.
