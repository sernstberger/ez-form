# v5 wave — form feedback & a11y, plus small housekeeping

Spec: none; authority is each GitHub issue plus the rulings here and `docs/PHILOSOPHY.md`
(rules 1–5 and the "a component ships when" checklist are binding). Base: 9b45774.

## Global Constraints

- `docs/PHILOSOPHY.md` rule 2: no `sx`, ripple props, or theme-unreachable literals in
  `src/`. Defaults via `useDefaultProps` + `styled` slots + `<name>Classes` +
  `src/theme/augmentation.ts`. A slot default spread under `slotProps` is the pattern.
- Rule 1: extend MUI / Base UI / react-hook-form types; never re-implement. Audit before changing.
- Rule 3: every component test keeps its jest-axe pass; pristine output (no `act()` warnings,
  no console noise — dev warnings added by Task 5 must be silenced in tests that trigger them
  on purpose and must not fire anywhere else in the suite).
- Rule 4: the form owns the lifecycle; fields read from context.
- **i18n-ready strings (for #23):** every new user-visible default string is a prop with a
  default value (`fooText = '…'`), never an inline literal in JSX, so #23 can route it
  through a locale table later. Announcement strings that interpolate values take a
  function prop (`(ctx) => string`) with a default implementation.
- A consumer's explicit prop always wins over any default this wave adds.
- Tests: vitest + Testing Library + jest-axe. `pnpm typecheck && pnpm test` before every
  commit; `pnpm format`; `node scripts/check-guardrails.mjs` clean.
- README: a row/section for any new prop or behaviour a consumer can see.
- Commit per task, conventional prefix, `Closes #N` (one `Closes` line per issue).
- No subagents from implementers. Do not touch `.superpowers/`, other worktrees, or `main`.

### Task 1: Shared live region + async submit status announcements (#3)

Files: `src/Form/LiveRegion.tsx` (new), `src/Form/Form.tsx`, `src/Form/Form.test.tsx`,
`src/Form/Form.stories.tsx`, `src/theme/augmentation.ts`, `src/index.ts`, README.

Requirements:
1. Audit first: `FieldArray`, `PasswordStrength`, `ResendCodeButton` and the SignUp example
   already render ad-hoc `aria-live` / `role="status"` nodes. Build one `LiveRegion`
   component (`EzLiveRegion`: `styled` root with a visually-hidden default style block so a
   theme can override it; `liveRegionClasses`; augmentation entry) plus a tiny
   `useAnnounce()`-style hook or `<LiveRegion message>` API — pick the simpler one that the
   three existing call sites can adopt. Migrate those three `src/` call sites to it (the
   example may stay). `politeness` defaults to `polite`.
2. `Form` renders one `LiveRegion` (inside the form, after the children, before the actions
   slot if there is one) and announces: submit started, submit succeeded, submit failed.
   Strings are props on `Form` with defaults: `submitPendingText = 'Submitting…'`,
   `submitSuccessText = 'Submitted.'`, `submitErrorText = 'Submit failed.'`; `false`
   suppresses an individual message. Announce via the existing lifecycle (the `isSubmitting`
   / `isSubmitSuccessful` / `onSubmitError` plumbing already in `Form.tsx`); do not add a
   second submit tracker. A validation failure (schema rejects, no submit call) is NOT
   "submit failed" — `FormErrorSummary` already covers it; announce nothing there.
3. The same message twice in a row must re-announce (clear then set, or key the node) —
   a second failed submit must be heard.
4. Tests: each of the three messages appears in the live region under the matching
   lifecycle; `false` suppresses; repeat announcement re-fires; axe clean; the migrated
   components' existing tests pass unmodified.
5. Export `LiveRegion`, its props type and `liveRegionClasses` from `src/index.ts`.

### Task 2: Focus and announcement on wizard step change (#2)

Depends on Task 1 (`LiveRegion`). Files: `src/Wizard/Wizard.tsx`, `src/Wizard/WizardStep.tsx`,
`src/Wizard/Wizard.test.tsx`, README Wizard section.

Requirements:
1. When the current step changes through Next/Back/`goTo` (not on initial mount, not on a
   failed-submit jump that `FormErrorSummary` already focuses), focus moves to the step's
   heading (the legend heading `WizardStep` renders, or the `aria-labelledby` target in the
   vertical layout). Where there is no heading element, focus the step's fieldset with
   `tabIndex={-1}`. Focus the container, not the first field: APG guidance for multi-step
   forms, and focusing a field would announce it before its step context.
2. Announce through the shared `LiveRegion`: default `stepAnnouncement =
   ({ index, count, label }) => \`Step ${index + 1} of ${count}${label ? `, ${label}` : ''}\``;
   `index`/`count` are computed over the *effective* (conditional `when`-filtered) step list.
   `stepAnnouncement={false}` disables it. Prop lives on `Wizard`.
3. The failed-final-submit jump (navigates to first errored step) must still let
   `FormErrorSummary` take focus — assert focus is on the summary heading in that case, not
   the step heading.
4. Tests: focus lands on the heading after Next and Back; announcement text for both
   layouts; conditional-steps count excludes hidden steps; `false` disables; initial mount
   does not steal focus; axe clean.

### Task 3: `actionsOrder` for WizardNav and ConfirmDialog (#5)

Files: `src/Wizard/WizardNav.tsx`, `src/ConfirmDialog/ConfirmDialog.tsx`, their tests and
stories, `src/theme/augmentation.ts`, README.

Requirements:
1. `ConfirmDialog` gains `actionsOrder?: 'cancel-confirm' | 'confirm-cancel'` (default
   `'cancel-confirm'`, Material). `WizardNav` gains `actionsOrder?: 'back-next' | 'next-back'`
   (default `'back-next'`). Both flow through the component's existing `useDefaultProps`
   registration (`EzConfirmDialog`, `EzWizardNav`) so `theme.components.<key>.defaultProps
   .actionsOrder` sets it globally; add the prop to the augmentation types if the props
   interface is not already what `ComponentsPropsList` points at.
2. The order is realised by rendering the buttons in a different DOM order — no
   `flex-direction: row-reverse`, no `order:` — so tab order matches visual order.
   `ConfirmDialog`'s "Cancel gets `autoFocus`" rule is unaffected by order.
3. `Form confirm`, `ClearButton confirm` and `useConfirm` all go through `ConfirmDialog`;
   confirm that a theme-level `EzConfirmDialog.defaultProps.actionsOrder` reaches all of them
   (one test through `Form confirm` is enough).
4. Tests: DOM order of the two buttons for each value; theme `defaultProps` path; axe clean.
   Story: one per component showing the reversed order.

### Task 4: `autoComplete` and `inputMode` defaults by field type (#6, #7)

Files: `src/fields/TextField/TextField.tsx`, `NumberField`, `MoneyField`, `OtpField`,
`PasswordField` (audit only), the pickers (audit only), their tests, README.

Requirements:
1. `TextField`: derive defaults from `type` when the consumer sets neither prop:
   `email` → `autoComplete="email"`, `inputMode="email"`; `tel` → `"tel"`/`"tel"`;
   `url` → `"url"`/`"url"`; `search` → `inputMode="search"`. Other types: no default
   (do not guess `name` → token; a wrong token is worse than none).
2. `NumberField` → `inputMode="decimal"` unless the field is integer-only (no fractional
   `step` / a `format` with 0 fraction digits — use whatever the component already knows),
   then `numeric`. `MoneyField` → `inputMode="decimal"`. `OtpField` → `inputMode="numeric"`
   and `autoComplete="one-time-code"` (check what Base UI already sets; do not duplicate).
3. `PasswordField` already sets `autoComplete="current-password"` — leave it; README shows
   `autoComplete="new-password"` for sign-up (verify the SignUp example does this; fix if
   not).
4. Attributes go on the real `<input>` through the existing `slotProps.htmlInput` /
   `inputProps` path each component already uses; a consumer's explicit `autoComplete` /
   `inputMode` (top-level or inside `slotProps.htmlInput`) always wins.
5. Tests: attribute on the DOM input for each mapping; consumer override wins; nothing
   emitted for plain `type="text"`.
6. README: a short "Mobile keyboards & autofill" table listing the defaults. Note the v8
   fields (#16–#19) will extend the table.

### Task 5: Dev-mode a11y warnings (#8)

Files: `src/devWarn.ts` (new), `src/fields/useEzField.tsx`, `src/fields/Option.ts` (or the
option-consuming fields), `src/Wizard/Wizard.tsx`, tests, README (Developer warnings section).

Requirements:
1. `devWarn(key, message)`: `console.warn` once per `key` per session, only when
   `process.env.NODE_ENV !== 'production'`; the check must be statically strippable
   (a top-level `const isDev = process.env.NODE_ENV !== 'production'` guarded call) so the
   production bundle carries no strings. Export nothing public.
2. Warn when: (a) a field mounts through `useEzField` with no accessible name — no `label`,
   no `aria-label`, no `aria-labelledby` (accept the props the hook already sees; do not
   query the DOM); (b) `Select`, `RadioGroup`, `Autocomplete`, `ToggleButtonGroup`,
   `CheckboxGroup` receive `options` with duplicate `value`s (one shared helper called from
   each); (c) a wizard step's `fields` lists a name that is not mounted when Next validates
   it — use `control._names.mount` (RHF's registered-names set; note in a comment that it is
   an internal-but-stable API) and skip the check when the set is empty.
3. Tests: each warning fires once with the field/step name in the message; does not fire
   for the valid case; a `NODE_ENV=production` test (stub `process.env`) fires nothing.
   Suite-wide: the rest of the test run must not emit any new warnings — run the whole
   suite and fix any story/test fixture that trips (a) or (b) rather than muting it.

### Task 6: Required indication beyond the asterisk (#4)

Files: `src/Form/Form.tsx`, `src/Form/Form.test.tsx`, `src/Form/Form.stories.tsx`, README.

Requirements:
1. `Form` already has `requiredIndicatorText` (rendered only in `requiredIndicator=
   "optional"` mode, default "All fields are required unless marked optional."). Extend it to
   `asterisk` mode with a mode-dependent default: `'Fields marked * are required.'`. The
   existing rendering path (description slot / legend) is reused; `false` hides it in either
   mode; an explicit string is used verbatim in either mode.
2. The `*` inside the instruction is visual only: wrap it so AT reads the sentence sensibly
   (MUI's `FormLabel` asterisk is `aria-hidden`; mirror that — e.g. `<span aria-hidden>*</span>`
   with a visually-hidden "asterisk" alternative, or phrase it as "Required fields are marked
   with an asterisk (*)"). Pick one; the ruling below defaults to the phrasing approach.
3. Per-field: no extra hidden "required" text — the input already carries `required` /
   `aria-required`, so AT announces it; adding text would double-announce.
4. Tests: default text in asterisk mode; `false` hides; custom string; optional-mode default
   unchanged; existing Form/Wizard/example tests that snapshot or query form text are
   updated, not weakened; axe clean. Story updated.

### Task 8: `FormDialog` — form in a MUI Dialog with exit confirmation (#22)

Files: `src/FormDialog/FormDialog.tsx` (new), `FormDialog.test.tsx`, `FormDialog.stories.tsx`,
`index.ts`, `src/theme/augmentation.ts`, `src/index.ts`, README (new section + Components row).

Requirements:
1. `FormDialog` = MUI `Dialog` whose paper is the `<Form>` element: props are
   `Omit<DialogProps, 'onClose' | 'open' | 'slotProps'> & FormProps` plus `open`,
   `onClose`, `title` (rendered as `DialogTitle`, wired to `aria-labelledby`), `actions`
   (rendered in `DialogActions`; defaults to a `ClearButton`-free `SubmitButton` + a Cancel
   `Button`), and `exitConfirm?: ConfirmOptions | false`. Use `slotProps.paper = { component:
   Form, ... }` if it composes cleanly; otherwise render `Form` as the first child of
   `Dialog` with `DialogContent` inside. Audit `Form`'s `component`/`slotProps` first.
2. Closing while dirty (backdrop click, Escape, Cancel) opens `ConfirmDialog` with
   `exitConfirm` copy (default title "Discard changes?", confirm "Discard", cancel
   "Keep editing"); confirming calls `onClose`; not dirty → close immediately. Reuse
   `useConfirm` and the form's own dirty state (`useFormGuard` semantics: not dirty after a
   successful submit). `exitConfirm={false}` disables the prompt.
3. Successful submit closes the dialog (`onClose` with reason `'submit'`) unless
   `closeOnSubmit={false}`. Loading/disabled/confirm on `Form` keep working unchanged.
4. Theme: `EzFormDialog` with `useDefaultProps`, `styled` slots (`Root`, `Title`, `Content`,
   `Actions`), `formDialogClasses`, augmentation entry.
5. Tests: dirty → Escape prompts; confirm discards; cancel keeps; clean → Escape closes;
   submit closes; `exitConfirm={false}`; focus returns to the opener after close; axe clean
   (dialog open). Stories: basic, with confirm, long content scroll.

## Rulings (pre-flight)

- Ruling: one `LiveRegion` component replaces the three ad-hoc live nodes in `src/` — rule 1,
  and #3's issue text asks for the shared utility — cost if wrong: three small migrations to
  revert.
- Ruling: step change focuses the step heading, not the first field — APG multi-step focus
  management; announces context before content — cost if wrong: one extra Tab for keyboard
  users.
- Ruling: `actionsOrder` values are named by button order (`'cancel-confirm'`, `'back-next'`),
  not by platform (`'material'` / `'windows'`) — self-describing, no cultural lookup — cost if
  wrong: rename before publish.
- Ruling: `autoComplete`/`inputMode` derive from `type` on `TextField`, never from `name` —
  a wrong token is worse than none — cost if wrong: consumers set the prop (one attribute).
- Ruling: dev warnings use `control._names.mount` for the wizard check — RHF exposes no
  public "is mounted" API; the set is stable across 7.x — cost if wrong: guard by feature
  detection, warning silently off.
- Ruling: #4 ships a form-level instruction in asterisk mode ON by default via the existing
  `requiredIndicatorText` prop, phrased "Required fields are marked with an asterisk (*)."
  — WCAG 3.3.2 wants the convention stated; `false` turns it off; theme `defaultProps` sets it
  globally — cost if wrong: every existing form gains one line until a consumer passes
  `false`.
- Ruling: no per-field hidden "required" text — `aria-required` already announces — cost if
  wrong: AT that ignores `aria-required` (none current).
- Ruling: #71 keeps the `^18 || ^19` peer range and wraps in `forwardRef` — MUI 9 still
  supports 17–19, so narrowing has no upstream justification — cost if wrong: `forwardRef`
  boilerplate to remove when 18 is dropped.
- Ruling: #10 `ezFormTheme` and #11 reduced-motion, #43 subpath exports, and all
  `needs-design` issues (#14, #20, #21, #23, #47, #65, #79) wait for a brainstorm with Steve
  after this wave — they are taste/packaging decisions — cost if wrong: one wave's delay.
